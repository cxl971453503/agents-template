# 评估框架

## 定位

本文档为扩展能力，仅适用于需要量化评估 Agent 产出质量或建立质量门禁的项目。简单项目可沿用阶段 5 的审查清单。

## 评估维度

### 正确性

- 产出是否满足任务定义的目标和完成标准
- 变更是否与方案、契约和工程规范一致
- 评估方式：对照 `docs/task-board.md` 中的完成定义逐项检查

### 完整性

- MVP 功能是否全部覆盖
- 边界条件和错误态是否处理
- 文档同步是否完整
- 评估方式：对照 `docs/product-requirements.md` 和文档同步矩阵检查

### 可维护性

- 代码或产物结构是否清晰
- 关键逻辑是否有中文注释
- 是否存在不必要的复杂度
- 评估方式：参照 `docs/workflow/implementation-review-checklist.md`

### 安全性

- 是否存在注入、越权、敏感数据暴露等风险
- 输入验证是否充分
- 权限边界是否明确
- 评估方式：参照 OWASP Top 10 常见风险逐项检查

### 一致性

- 文档间是否矛盾
- 接口契约是否与实现匹配
- 术语使用是否统一
- 评估方式：交叉比对 `docs/architecture.md`、`docs/api-contracts.md` 和实际产出

## 评分标准

每个维度采用 3 级评分：

| 等级          | 含义                                 | 判定依据                               |
| ------------- | ------------------------------------ | -------------------------------------- |
| A（达标）     | 满足该维度全部核心检查项             | 无阻塞问题                             |
| B（基本达标） | 满足该维度大部分检查项，存在次要问题 | 无阻塞问题，有重要问题但已标注处理方案 |
| C（不达标）   | 存在阻塞问题或关键缺失               | 有阻塞问题未解决                       |

## 评估流程

1. Tester 在阶段 5 执行审查时，按 5 个维度逐项评分
2. 评分结果写入评审输出，替代或补充原有的问题清单
3. 各维度均为 A 或 B 时，评审结论为"可通过"
4. 任一维度为 C 时，评审结论为"需修改后再审"
5. 评估结果随阶段 6 交接文档沉淀

## 评估报告格式

```md
## 评估报告

### 评估对象

- 产物名称：
- 关联 Task ID：
- 评估时间：

### 维度评分

| 维度     | 等级 | 说明 |
| -------- | ---- | ---- |
| 正确性   |      |      |
| 完整性   |      |      |
| 可维护性 |      |      |
| 安全性   |      |      |
| 一致性   |      |      |

### 综合结论

- 评审结论：可通过 / 需修改后再审 / 存在风险但可接受
- 关键问题：
- 剩余风险：
```

## 与现有审查流程的关系

- 本框架不替代阶段 5 的审查清单，而是在其基础上增加量化评分
- 简单项目可继续使用审查清单，无需启用评分
- 启用评估框架后，Tester 的审查清单检查项自动映射到对应维度

## 启用条件

当项目满足以下任一条件时，建议启用评估框架：

- 项目有严格的质量门禁要求
- 需要向利益相关者量化交付质量
- 多轮迭代中需要对比质量趋势
- 团队规模较大，需要统一质量标准
